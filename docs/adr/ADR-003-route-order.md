# ADR-003. Порядок правил: прямой маршрут раньше блокировки IPv6

Дата: 15.11.2026, версия 0.2.0

## Проблема

Правила в конфиге sing-box лежали в таком порядке:

1. `sniff`
2. `hijack-dns`
3. `ip_is_private → direct`
4. `ip_version: 6 → reject` (если включена блокировка IPv6)
5. `process_name: [...] → direct` (приложения, которые идут напрямую)

Правила проверяются сверху вниз, поэтому для исключённой программы любой
IPv6-трафик попадал в пункт 4 и **отбрасывался**, не доходя до пункта 5.
Итог: программа, которую владелец явно отправил «напрямую», теряла IPv6 —
её соединения рвались или замедлялись, а разбираться в этом должен был он.

Замечено при проверке: браузер и служебные клиенты, исключённые из туннеля,
теряли IPv6-соединения, хотя блокировка IPv6 нужна только внутри туннеля.

## Решение

Правило прямого маршрута поднято выше блокировки IPv6:

1. `sniff`
2. `hijack-dns`
3. `ip_is_private → direct`
4. **`process_name: [...] → direct`**
5. `ip_version: 6 → reject`
6. `final: proxy`

Смысл: «напрямую» — значит совсем напрямую, со своим стеком, включая IPv6.
Блокировка IPv6 остаётся для всего, что идёт через туннель, то есть
защищает от утечки мимо туннеля.

## Альтернативы и почему нет

- **Не блокировать IPv6 вообще.** Тогда IPv6-трафик уходит мимо туннеля у всех
  программ: настоящая утечка. Отклонено.
- **Отдельный список исключений через WFP.** Правильный, но это отдельный
  привилегированный компонент; для 0.2 избыточно. Отложено до WFP-этапа.
- **Отключить блокировку IPv6, если есть исключения.** Ломает защиту у всех
  остальных программ. Отклонено.

## План отката

Одна правка: вернуть `ip_version: 6 → reject` выше правила `process_name`.
Тест `split_rule_reaches_direct_outbound` сразу покажет нарушение порядка.

## Проверка

- Тест проверяет не только наличие правил, но и их взаимный порядок:
  `direct_at < v6_at`.
- Живой туннель: исключённый клиент ходил напрямую, неисключённый — через
  сервер; обе стороны работали одновременно.
